# Nelli-Dev document templates

Copy the block, fill every section, delete none (write "None" instead).

## Closing lines for EVERY document (after the template's last section)

```
Checked: references re-checked — yes | partly (<which not>) · verified live — yes (<environment>, <date>) | no · gaps — <list, or none>
> Generated by Nelli-Dev <plugin version>, knowledge <version/date>. Confidence NN%. Human review and testing required before production use. Not a substitute for Znode documentation or support.
```

The stamp is never typed from memory and the version is never hard-coded: print it with
`python ${CLAUDE_PLUGIN_ROOT}/scripts/nd_integrity.py stamp --confidence NN --format block` (it reads the plugin version and the knowledge date at run time)
and paste its output. NN is the lowest confidence among the document's verdict-deciding statements. Before a document is handed over, scan it:
`python ${CLAUDE_PLUGIN_ROOT}/scripts/nd_secret_scan.py <document or folder>` must exit 0 (no tokens, keys, connection strings, e-mail addresses or host names; use `$ZNODE_API_TOKEN`-style placeholders and environment names).

```
# Requirements — <REQUEST-ID>: <title>
Requested by · Date · Znode version · Environment · Source (chat / FSD path)

## Functional requirements
| # | Requirement | Source (FSD section / developer message) |
## Acceptance criteria
| AC | Criterion (testable) | Must-pass |
## Constraints (performance, security, compliance, deadlines, existing customizations)
## Assumptions (each with confidence)
## Open questions (each with the options offered)
```

## T2 discovery.md

```
# Discovery — <REQUEST-ID>
## Registry lookups (nd_registry.py find/show: query → entries)

```

## T3 solution-proposal.md

```
# Solution proposal — <REQUEST-ID>: <title>
## Verdict: Supported | Customizable | Restricted | Needs platform change   (applies to Znode <version>)
Evidence for the verdict: <registry id(s) + KB/API link or file:line>
## Options considered
| Option | How | Pros | Cons / risks | Verdict |
## Recommended approach
Why this option. Where the logic lives and why (consistency across listing, cart, checkout where relevant).
## Design
Components and files · data flow (numbered steps, incl. each API call) · API contracts (request/response fields) · configuration · security and tenancy design · caching
## Impact on existing functionality
## Out of scope
## Limitations and upgrade risk (Webstore source changes: state the merge risk)
## Effort estimate (for a developer new to Znode) and risks
## Open questions / items needing confirmation
```

```

## Configuration and environment variables (names only, never values)

## Recommendations and follow-ups
## Responsibilities
| | |
|---|---|
| What Nelli-Dev did | <analysis, files generated or changed (list), tests written, scans run: each with its path> |
| What Nelli-Dev did NOT do | <anything not built, not run, not verified live; platform behaviour it could not see> |
| What you (the developer) must verify | review every changed file; run the build and the tests in your own environment; check authorization and ownership logic; test on a non-production environment; confirm the items marked needs confirmation |
| Approvals recorded | <approval.json: who, when, scope; each stop the developer approved: commit / push / deploy / data-changing test> |
| Open risks you accepted | <findings accepted in writing, with name and date, or none> |
## Version stamp
```
